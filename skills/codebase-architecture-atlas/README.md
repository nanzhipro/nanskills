# Codebase Architecture Atlas

**把陌生代码库变成一张可以探索、追问和复查的系统地图。**

Codebase Architecture Atlas 是一个面向 AI Agent 的代码库理解 Skill。它从当前代码中提炼系统参与者、模块边界、协作关系、关键数据流和设计原则，最终生成可逐层下钻的交互式架构大图。

## 核心特性

- **证据驱动**：关键实体和关系可以回到文件、类型、协议或配置。
- **分层理解**：从系统全景进入模块拓扑、模块内部和运行时数据流。
- **项目化建模**：使用代码库自己的角色与术语，不套用固定技术词表。
- **交互式阅读**：支持详情查看、双击下钻、全局搜索、平移缩放和链接定位。
- **诚实表达现状**：同时呈现设计原则、历史债务、例外路径和不确定项。
- **便于分享**：交付可维护的源工程和可独立打开的单文件 HTML。

## 快速开始

### 运行要求

- 能够加载本地 Skill 并执行代码勘探任务的 AI Agent
- Node.js 18 或更高版本，用于数据与布局检查
- Python 3.9 或更高版本，用于本地预览和离线版打包
- 本机 Chrome，用于最终截图与视觉验收

### 安装

将完整目录放入 Agent 能够发现的 Skill 目录，并保留 `SKILL.md`、`assets/`、`references/` 和 `scripts/` 的相对结构。

Codex 默认使用：

```text
$CODEX_HOME/skills/codebase-architecture-atlas/
```

未设置 `CODEX_HOME` 时，默认位置是：

```text
~/.codex/skills/codebase-architecture-atlas/
```

其他 Agent 可能使用：

```text
~/.agents/skills/codebase-architecture-atlas/
```

不同 Agent 的 Skill 根目录可能不同，以其本地配置为准。安装后开启新会话或重新加载 Skill 列表，确认 `codebase-architecture-atlas` 可以被识别。

### 使用

直接向 Agent 描述代码库位置和理解目标：

```text
为这个代码库生成一张交互式架构大图，重点说明进程边界、关键数据流和历史债务。
```

也可以收窄范围：

```text
深入理解认证链路，从入口、策略判断、状态存储到外部依赖画出完整架构。
```

```text
比较这几个仓库在整个产品中的职责，并标出跨仓通信关系。
```

```text
以最新代码为准更新现有 Atlas，并说明架构发生了什么变化。
```

最少只需提供代码库或 workspace 的位置。为了获得更贴近决策场景的结果，还可以补充：

- 最关心的业务链路或技术风险
- 希望覆盖或排除的仓库、目录和生成代码
- Atlas 的主要读者，例如研发、架构师、安全团队或新成员
- 已有文档、历史结论，以及需要重点核实的假设

## 从用户视角

### 它解决什么问题

接手一个陌生代码库时，最难的通常不是找到文件，而是建立可信的系统认知：

- 系统由哪些进程、服务、模块、存储和外部依赖组成？
- 一次关键业务动作会经过哪些组件和边界？
- 哪些模块是核心，哪些只是适配层、工具或历史遗留？
- 部署边界、权限边界和通信边界在哪里？
- 文档描述与当前代码是否一致？
- 哪些设计原则值得保留，哪些架构债务需要优先处理？

这个 Skill 会把答案组织成一张可探索的系统地图。你可以先建立全局认知，再进入相关模块，最后沿关键数据流检查一次运行时协作是否形成完整闭环。

### 适用场景

- 接手或评审一个不熟悉的中大型代码库
- 理解多仓库、多进程、多服务或插件化系统
- 为架构评审、技术交接、重构规划建立共同语境
- 追踪跨模块、跨进程、跨网络的数据流
- 核对现有架构文档是否符合最新代码
- 在安全审计或故障分析前建立系统全景

单文件脚本或结构非常简单的 CRUD 应用通常不需要完整 Atlas。

### 交付内容

| 你想知道 | Atlas 中的对应内容 |
|---|---|
| 系统整体由谁组成 | 全景总览 |
| 模块如何划分、边界在哪里 | 模块拓扑 |
| 一个模块内部如何协作 | 模块内部视图 |
| 一次关键动作如何发生 | 数据流时序 |
| 为什么这样设计 | 设计原则 |
| 哪些地方值得警惕 | 债务、例外与不确定项 |
| 结论依据是什么 | 组件详情中的关键文件与证据 |

一次完整交付通常包括：

- 可交互浏览的 Atlas 源工程
- 可双击打开、便于分享的单文件离线版 HTML
- 必要时保留的代码勘探记录
- 实体、关系和关键数据流的统计摘要
- 已知局限、未确认事项与后续建议

### 阅读顺序

1. 从全景总览确认系统参与者和产品边界。
2. 进入与当前问题相关的模块，理解它在系统中的职责。
3. 点击组件查看证据、部署信息、上下游关系和备注。
4. 沿数据流时序检查关键动作的完整路径。
5. 阅读设计原则和债务，区分有意设计、现实约束与历史遗留。

## 从 Skill 视角

### 建模原则

Skill 的任务不是“读目录后画图”，而是建立一个有证据支撑、可以回到源代码复查的系统模型。

1. **证据优先**：无法确认的内容会标为不确定，而不是补全想象。
2. **使用项目自己的语言**：从当前代码归纳角色和关系，不把模板词表强加给项目。
3. **先建立全景，再逐层深入**：同一模型服务于全局理解、模块分析和运行时追踪。
4. **把例外也当作架构事实**：死代码、兼容层、历史命名、版本错位和临时旁路都会如实记录。
5. **把可读性视为正确性的一部分**：交付前检查结构、布局、标签和下钻路径。

### 工作方式

| 阶段 | Skill 在做什么 | 用户可以观察到什么 |
|---|---|---|
| 范围建立 | 识别仓库、边界、读者和核心问题 | 覆盖范围与重点清晰 |
| 代码勘探 | 分区域追踪实体、接口、调用和部署关系 | 结论带有代码证据 |
| 架构建模 | 用项目语言归纳实体、关系、数据流和原则 | 图例与项目实际一致 |
| 叙事组织 | 把同一模型编排为全景、模块和时序视图 | 可以从问题逐层下钻 |
| 质量验证 | 检查引用、结构、布局和实际呈现 | 图可打开、可浏览、无明显歧义 |
| 交付说明 | 汇总统计、局限和未确认事项 | 知道哪些可信、哪些仍需核实 |

对于大型 workspace，Skill 会把勘探任务拆成多个相对独立的区域，并重点核对跨仓库、跨进程或跨服务边界。并行勘探用于减少单一路径造成的遗漏，最终结果仍会合并进同一个模型并统一复核。

### 证据边界

- **事实**：当前代码、配置、构建文件或协议直接证明的内容，进入主体模型。
- **推断**：由多个证据综合得到但没有直接声明的结论，保留依据和不确定性。
- **目标设计**：面向未来的建议不会伪装成现状；涉及改造方案时，与当前 Atlas 明确分开。

## 验收标准

一张合格的 Atlas 应该让读者回答以下问题：

- 能否在几分钟内说清系统边界和核心参与者？
- 能否沿图追踪最重要的运行时链路？
- 每个关键结论能否回到代码证据？
- 图中的角色和术语是否符合项目实际？
- 不确定项、历史债务和异常路径是否被诚实呈现？
- 不同层次之间能否自然下钻，而不是重复同一张图？
- 离线版能否正常打开、搜索和查看详情？

如果答案是否定的，Atlas 仍需继续补充证据、重组视图或修正表达。

## 能力边界

- Atlas 描述指定代码快照，不自动代表生产环境的实时状态。
- 代码可以证明设计和调用关系，但不一定能证明某条路径已在生产环境成功运行。
- 动态注册、运行时注入、远端配置和环境差异可能需要日志或部署证据补充。
- Atlas 用于建立系统认知，不能替代专项性能分析、安全验证或故障复现。

## 已验证场景

该 Skill 首次在 macOS 安全软件 Santa 上完成端到端验证，覆盖多进程、系统扩展、命令行工具、策略服务和复杂通信关系。该案例验证了对复杂系统进行分层表达、证据回溯和关键数据流组织的能力。

## 设计参考与优化方向

2026-08 深度分析了 [tt-a1i/archify](https://github.com/tt-a1i/archify)（MIT, v2.15）后形成的判断：archify 的竞争力不在画图，而在「交付前可验证、交付后有证据」的可信度工程。Atlas 的本体论勘探（勘探推导词表、四层纵深、多仓适配）比 archify 的固定 7 类组件枚举更深，保持差异；补上 archify 的验证收据、原子交付、真话交互、证据溯源四大机制。

| 阶段 | 内容 | 状态 |
|---|---|---|
| P0 | 验证收据化：validate/lint 输出升级为「规则码 + 带 id 的 subject 路径 + evidence + supportedFixes」；修正轮次上限 2 轮；验证通过即冻结候选 | 待实施 |
| P1 | 原子交付：候选快照 → 全检查通过才替换；SHA-256 收据；shoot 截图输出结构化 JSON 证据并声明 `visual_review: pending`；质量分档 standard/showcase | 待实施 |
| P2 | 真话交互（reach/route 只复用已创作关系）；源码证据 SRC 标记 + commit 钉扎；Before/Delta/After 对比；普通模型一次通过率基准 | 按需 |
| P3 | 场景速查表、设计令牌抽取、Mermaid 输入、图内文案跟随用户请求语言 | 随手做 |

完整分析报告：`~/workspace/docss/2026-08-21/archify-洞察与atlas优化规划.md`。不采纳项：typed JSON Schema 生成器（data.js 保持灵活性）、五图类型扩展（四层纵深是差异化）、固定组件类型枚举（勘探词表更强）。
